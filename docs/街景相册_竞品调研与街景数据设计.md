# 街景相册：竞品调研与街景数据设计（东京 / 大阪 / 奈良 / 京都 / 镰仓）

> 2026-11-17 · 产品概念：用户导入照片 → 读取照片 EXIF 地理位置信息 → 从地图服务获取该位置街景 → 用户照片浮于街景之上，边看街景边回忆旅行。

> **⚠️ 方向调整（2026-11-17）**：因街景图像仅允许 30 天缓存（不能持久保存）+ 大陆网络不可直连 Google，项目转向 **2D 足迹相册**。本文档的竞品调研、五城点位盘点、"照片→位置→聚类"流程设计仍然适用（仅底图从街景换为地图瓦片），保留作为存档。

---

## 一、竞品检索结论：目前没有产品完整实现这个功能

检索范围：iOS/Android 应用、Google Play / App Store、GitHub 开源项目、旅行日志类产品。

| 现有产品 | 相似点 | 缺口（与"街景相册"的差异） |
|---|---|---|
| Google Photos「地图视图」 | 照片按 EXIF 定位钉在地图上 | 只有 2D 地图打点，无街景、无浮层 |
| [Footprint Map 旅行足迹地图·相册](https://play.google.com/store/apps/details?id=com.jcstudio.footprintmap)（Android） | 按照片时间+位置自动生成足迹地图与旅行相册 | 足迹在地图上"点亮"，不涉及街景 |
| [PhotoMap Local](https://apps.apple.com/us/app/id6760936129)（iOS）/ [PhotoMap Gallery](https://play.google.com/store/apps/details?id=eu.bischofs.photomap)（Android） | 离线照片地图、小旗子标记、旅行日记 | 同上，止步于 2D 地图 |
| [Polarsteps](https://www.polarsteps.com) | 自动记录路线、照片挂到行程地图 | 旅行社区向，无街景浮层概念 |
| [Time Portal 历史照片](https://apps.apple.com/us/app/id1101646259)（iOS） | "今昔对比"：地图上浮出历史老照片 | 用的是档案老照片，不是用户自己的照片；底图非街景 |
| [GeoPhoto](https://apps.microsoft.com/detail/9wzdncrfj0f2)（Windows） | 照片钉在地图上，集成 Bing Streetside 街景 | 定位是"看照片在哪"，不做照片浮于街景的回忆相册 |
| [Google 街景官方](https://www.google.com/intl/zh-CN/streetview) | 「Back in Time」可回看同一地点多年街景（[官方博客](https://blog.google/products-and-platforms/products/maps/go-back-in-time-with-street-view)） | 只能浏览官方全景，不能叠加个人照片 |
| [StreetLens](https://github.com/tjhorner/streetlens)（开源） | 自托管，地理照片 + 全景查看器 | 是 OSINT/浏览工具，不是相册产品 |

**附加发现**：GitHub 上已有开源项目验证了"照片 ↔ 街景"自动匹配的技术可行性——OSINT 领域的 image-geolocation 工具（MegaLoc、MASt3R 等）能把一张照片与街景全景做视觉匹配反查坐标（见 [GitHub topic: image-geolocation](https://github.com/topics/image-geolocation)）。这说明"照片自动对齐街景视角"在技术上不是空中楼阁。

**结论**：
- "照片 → 地图相册"已是成熟品类（Footprint Map / PhotoMap / Polarsteps），但全部止步于 2D 地图。
- "街景"与"个人照片"目前只在 GeoPhoto / OSINT 工具里有浅层结合。
- **"用户照片浮于同位置街景之上"作为核心体验的产品，未检索到现成实现** → 立项方向成立，且"今昔对比"（照片拍摄日期 vs 街景拍摄日期）是与所有竞品差异化的记忆点。

## 二、街景数据源选型（面向日本五城）

| 数据源 | 五城覆盖 | 接入方式 | 费用 | 许可/存储 | 备注 |
|---|---|---|---|---|---|
| **Google Street View**（首选） | ★★★★★ 全覆盖，含步行道、寺社参道、千本鸟居（[伏见稻荷全景](https://artsandculture.google.com/streetview/fushimi-inari-shrine/fwEhfEiGDJ8NQQ)） | Street View Static API（取图）；Maps JavaScript API（交互全景） | [Essentials 档](https://developers.google.com/maps/documentation/streetview/usage-and-billing)：每月 1 万次免费调用，之后约 $7/千次（[官方定价](https://mapsplatform.google.com/pricing)）；metadata 查询不计数 | ⚠️ 已核实（[Service Specific Terms](https://cloud.google.com/maps-platform/terms/maps-service-terms)）：街景图像**最多可缓存 30 个连续日历日，之后必须删除**；不可作为相册资产永久存图。坐标、pano_id、拍摄日期等元数据的长期保存属"事实性数据"，风险低 | 唯一同时具备"覆盖广 + 多年历史影像（Back in Time）"的源；2008 年起在日本多轮重拍 |
| **Apple Look Around**（备选） | ★★★★ 覆盖五城主要城区，画质高 | [MapKit JS LookAround](https://developer.apple.com/documentation/mapkitjs/lookaround)（官方支持 web 取景，[示例代码](https://developer.apple.com/maps/sample-code/interactive-look-around)） | 需 Apple Developer Program，配额以官方为准 | 不可下载存储 | 无历史影像；大陆网络下 Apple 服务可达性优于 Google |
| **Mapillary**（补充） | ★★ 有覆盖但密度不均、以车行为主（[日本研究](https://d-nb.info/1265102023/34)） | [API v4](https://www.mapillary.com/developer/api-documentation)（免费 token） | 免费 | **CC-BY-SA，可下载存储**，适合需要离线持久化的场景 | 步行景点覆盖差，只能当兜底素材库 |
| 百度/高德/腾讯街景 | 无日本街景 | — | — | — | 国内厂商均无日本街景数据，不在选型内 |

**关键决策点**：
1. 目标用户在哪 —— Google API 在中国大陆不可直连；若面向国内用户，要么接受"需科学上网"，要么主走 Apple Look Around / Mapillary 路线。
2. 街景图要不要"存进相册" —— Google 条款限制持久化存储；Mapillary 允许存储但日本步行景点没图。**MVP 建议：在线渲染为主（Google），用户手动"收藏"的页面考虑允许受限缓存，正式商用前找 Google 确认条款。**

## 三、五城市街景覆盖盘点

Google 在日本投入了街景车 + Trekker 背包采集，五个城市覆盖程度均为世界顶级水平，且**步行景点内部**多有全景。按"照片最可能拍在哪"盘点：

### 东京（覆盖最深，历史影像最多）
- **代表点位**：浅草寺雷门·仲见世通（步行全覆盖）、涩谷十字路口、新宿东口、东京站丸之内、皇居外苑、谷中银座、神保町、台场。
- **特点**：2008 年起多轮重拍，同一地点常有 5+ 个年份的全景 → 最适合"当时这条街"的时间胶囊功能。
- **风险**：无显著风险；高楼峡谷区全景密度高，反而有利于就近匹配。

### 大阪
- **代表点位**：道顿堀戎桥（格力高招牌，街景标志性点位）、新世界·通天阁、大阪城公园+天守阁周边、梅田、中之岛、黑门市场（商店街内有覆盖，需实测）。
- **风险**：环球影城（USJ）园区内部无街景 → 需要设计"最近路口街景 + 距离提示"的降级展示。

### 京都（步行景点最密集，Trekker 覆盖最典型）
- **代表点位**：清水坂·产宁坂·清水寺境内、**伏见稻荷千本鸟居**（[有官方全景](https://artsandculture.google.com/streetview/fushimi-inari-shrine/fwEhfEiGDJ8NQQ)，含登山步道）、岚山竹林小径、金阁寺周边、鸭川沿岸、二年坂三年坂。
- **风险**：祇园花见小路 2019 年起禁止拍摄（私人道路），该巷内街景覆盖可能缺失或人脸模糊处理较重 → 兜底方案：显示东大路通路口的全景。
- **加分项**：樱花季/红叶季有专项采集 → 按照片季节匹配最近同季街景，怀旧效果最强。

### 奈良
- **代表点位**：奈良公园（有著名的鹿群全景）、东大寺大佛殿周边、春日大社参道、兴福寺、奈良町、三条通商店街。
- **风险**：公园深处、堂塔内部无覆盖 → 降级展示最近步道入口。

### 镰仓
- **代表点位**：若宫大路+段葛、鹤冈八幡宫参道与境内、小町通（部分）、高德院大佛、长谷寺、江之岛（弁天桥·参道·展望台）。
- **风险**：山道与寺内覆盖多为较早采集、密度一般；小町通等步行街为分段覆盖 → 用 metadata 探测自动找最近全景即可。

### 覆盖验证方法（写进开发流程）
不要依赖文档描述，用 **Street View Static API metadata 探测**逐点验证：向 metadata 端点发坐标（radius 30m → 100m 递增，`source=outdoor`），返回 `status=OK` 即有覆盖，同时拿到 `pano_id` 与 `imageDate`。这个接口不消耗计费配额，适合批量预检。

## 四、核心技术流程设计

```
照片导入 → EXIF 解析(GPS / GPSImgDirection / DateTimeOriginal)
        → 按时间+位置聚类成"旅行段"
        → 对每张照片做街景探测(metadata, 免费配额)
             ├─ 命中：记录 pano_id + imageDate + 实际偏移距离
             └─ 未命中：降级为地图卫星视图 + 位置标记
        → 相册页：街景全景为底，照片卡浮层
```

**照片浮层的三种模式（由易到难）**：
1. **相框模式（MVP）**：全景铺满，照片卡片浮于角落，带拍摄时间与连线指向取景点位。
2. **今昔对比模式**：利用街景 `imageDate` 与照片 `DateTimeOriginal` 就近匹配（含季节匹配），左右分屏滑动对比；数据源明确支持（Google Back in Time 自 2007 年起的历史影像，[官方文档](https://developers.google.com/maps/documentation/earth/historical-street-view)）。
3. **视角对齐模式（V2）**：优先读 EXIF `GPSImgDirection`（多数手机已记录拍摄朝向）直接对齐全景 heading；进阶方案用图像 embedding 与全景多角度切片匹配，自动找"当年站在哪里拍的"（MegaLoc/MASt3R 类开源工具已验证可行性）。

**选图策略**：同一坐标可能有多个全景（不同年份/不同车道）→ 按 `(距离, |照片日期 - 街景日期|, 是否同季)` 打分排序，默认给"日期最近"的，用户可切换年份。

## 五、合规与风险清单

| 风险 | 说明 | 对策 |
|---|---|---|
| Google 条款限制存储 | **已核实**：街景图像最多缓存 30 个连续日历日，之后必须删除；不能永久存图 | 相册只存"指针"（坐标 / pano_id / 日期 / 朝向），街景打开时在线渲染；30 天缓存用于缩略图与弱网优化；离线/导出需求改用 Mapillary（CC-BY-SA）素材或不含街景的版本 |
| 全景退役 | Google 会更新/下架旧全景，存下的 pano_id 可能失效 | 每条记录同时存 `lat/lng + 照片日期` 作为兜底；pano_id 失效时按坐标+日期重新探测最近全景，并在 UI 上标注"街景已更新" |
| 计费失控 | 1 万次/月免费后 $7/千次；一张照片 = 1 次取图 | metadata 探测免费接口做预检；照片列表页只取低分辨率；加缓存层与预算告警 |
| 大陆网络 | Google API 大陆不可直连 | 明确目标用户；或提供 Apple Look Around 数据源切换 |
| 隐私地名（京都花见小路等） | 部分地点禁拍、街景覆盖缺失 | 城市点位包中标记 fallback 点位 |
| 无 GPS 照片 | 相机/截图/洗出来的扫描件无 EXIF | 支持手动选点放置；V2 可做"选相近照片传播 GPS" |

## 六、建议下一步

1. **建"城市点位包"**（本次"街景信息设计"的落地物）：五城各 20~50 个代表点位，JSON 格式 `{city, spot_name, lat, lng, fallback_pano_hint, notes}`，用于 demo 数据、探测脚本输入与 fallback 锚点。
2. **写探测脚本**：用 metadata 端点批量验证点位包，产出每点的 `pano_id / imageDate / 覆盖半径` 实测表，替换本文档中"需实测"的项。
3. **MVP 技术选型**：Web 优先（React + Maps JavaScript API 全景容器），照片本地处理不出设备；确认数据源（Google 在线 vs Apple）后再定移动端框架。
